# 13. 起動方式と権限モデルの再設計

調査日: 2026-09-25(第3回レビュー)

第2回までの設計で最大の難所だった「アセットを起動するタイミング」を前提から見直し、
あわせて「作成したカスタマイズ単位の権限(POST / PUT / DELETE の許可・禁止)」を新設する。
本書は判断の根拠と比較を残すための文書であり、確定した仕様は 03 / 04 / 05 / 06 / 07 / 08 / 11 へ反映済み。

## 1. 結論

| 論点 | 旧設計 | 新設計 |
| --- | --- | --- |
| 起動方式 | localStorageの同期キャッシュから即時実行 + showイベントのリプレイ | **起動ゲート**: showハンドラを同期登録し、初回showでPromiseを返してアセット取得完了まで保留する |
| 初回表示 | キャッシュが無いと間に合わない。リプレイはDOM副作用のみ | **初回から通常のカスタマイズと同じタイミング**。返却eventによる値変更・disabledも反映される |
| 無効化・権限剥奪の反映 | TTL(既定60分)〜hard expiry(24時間)まで古いコードが動きうる | **次の画面読み込みで必ず反映** |
| localStorageに置くもの | アセットのコード本文(他人に見せないprivateコードを含む) | ローカル無効化のID一覧とセーフモードのフラグだけ |
| アセットのイベント購読 | `context.on(...)`(独自API) | **標準の `kintone.events.on(...)`**。アセットへ渡す `kintone` をファサードに差し替える |
| カスタマイズ単位の権限 | なし(ユーザー権限で何でもできる) | **読み取りは常時許可。追加(POST)・更新(PUT)・削除(DELETE)・外部通信はアセットごとに許可制**。外部通信は「指定先のみ(URLで列挙)」か「すべて」を選べる。実装後もスイッチで切り替えられる |

## 2. 起動タイミング

### 2-1. 前提の見直し

旧設計は次の推論で同期キャッシュを採用していた。

> kintoneのイベントハンドラは発火前に登録されていなければ呼ばれない。
> アセットはRESTで非同期に取得する。したがって同期で読める場所(localStorage)にコードを置くしかない。

前半は正しいが、結論が飛躍している。**同期でなければならないのは「ハンドラの登録」であって、「コードの取得」ではない。**
kintoneは画面表示イベントでPromiseを返すと、その完了を待ってから後続の処理(次のハンドラ、返却eventの反映)へ進む。
プラグインが自分のshowハンドラを読み込み時に同期登録し、そのハンドラの中でアセットの取得完了を待てば、
アセットのハンドラは**そのshowイベントの処理の内側で**呼ばれる。

一次資料で確認した事実:

| 事実 | 出典 |
| --- | --- |
| PC版の `app.record.index.show` / `detail.show` / `create.show` / `edit.show` は**すべてPromise対応** | [イベントオブジェクトで実行できる操作](https://cybozu.dev/ja/kintone/docs/js-api/events/event-object-actions/) |
| `create.show` / `edit.show` では、返却eventによるフィールド値の上書き・disabled・エラー表示ができる | 同上 |
| `change` イベントはPromise非対応(同期で返す) | 同上 |
| show系ハンドラは、カスタマイズJSの読み込み時に同期登録すれば取りこぼさない。非同期処理の後で登録すると取りこぼしうる | [イベントハンドラー登録の適切なタイミング](https://cybozu.dev/ja/kintone/tips/development/customize/development-know-how/right-timing-of-kintone-event-handling/) |
| 上記の警告はshow系の遅延登録に限った話で、change / submit の登録時期には制約の記載がない | 同上 |
| `detail.show` はページ送り、編集画面での保存・キャンセル、プロセス実行後にも**同じページ内で**再発火する | [レコード詳細画面を表示した後のイベント](https://cybozu.dev/ja/kintone/docs/js-api/events/detail/detail-show-event/) |

> community.cybozu.dev には「`app.record.detail.show is not allowed to return "Thenable"`」という2018年の投稿があるが、
> 現行の公式表ではPC版のshow系はすべてPromise対応である。P-1で実機確認する(12章 P-1表)。

### 2-2. 比較した案

| 案 | 仕組み | 初回から間に合うか | 鮮度 | 主な代償 | 判定 |
| --- | --- | --- | --- | --- | --- |
| A. 同期キャッシュ(旧設計) | localStorageから同期実行 + リプレイ | ✕(2回目以降のみ) | ✕ 最大24時間古い | 容量5MB共有、eviction、共有PCの残留、同期予算、リプレイの半端な意味論 | 置換 |
| **B. 起動ゲート** | showを同期登録し、初回showでPromiseを返して取得を待つ | **◯** | **◯ 常に最新** | 取得がshowより遅いぶん、そのshowの完了が遅れる | **採用** |
| C. JSカスタマイズへ書き出す | `PUT /k/v1/preview/app/customize.json` + 反映 | ◯ | ◯ | **アプリ管理権限が必須**。反映APIは動作テスト環境の**全設定を一括で**本番へ出すため、他人が編集中のフォーム変更まで反映してしまう。「自分だけ」が作れない | 却下 |
| D. プラグイン設定に格納 | `getConfig` は同期で読める | ◯ | ◯ | 書き込みは設定画面か、API Labの `PUT /k/v1/preview/app/plugin/config.json`(本番未提供)のみ。どちらもアプリ管理権限と反映が必要 | 却下 |
| E. B + CSSだけキャッシュ | CSSのみ同期適用し、FOUCを消す | ◯ | CSSだけ古いものが一瞬出る | 実装が増える。コード本文を再び端末へ置く | P-1の結果次第の退避策 |

Cの「反映は全設定一括」は [アプリの設定を運用環境へ反映する](https://cybozu.dev/ja/kintone/docs/rest-api/apps/settings/deploy-app-settings/) で確認した。
一般ユーザーがカスタマイズを作れることが本プラグインの価値なので、アプリ管理権限を要求する案は根本的に合わない。

### 2-3. 起動ゲートの仕様

```text
desktop.js 読み込み(同期)
  ├─ 1. セーフモード判定。有効なら 2 以降は「ランチャーだけ」の経路へ
  ├─ 2. アセット取得を開始する(await しない)          ← kintone本体の初期化と並行に走る
  ├─ 3. show系4イベントへ native handler を同期登録
  │
kintone が app.record.<screen>.show を発火
  ├─ その画面種別で初めてのshow(= ゲート)
  │     └─ Promise を返す
  │          ├─ 取得完了を待つ(上限 GATE_TIMEOUT_MS)
  │          ├─ CSS: この画面向けの <style> を有効化
  │          ├─ JS : この画面向けで未評価のアセットを order 順に評価
  │          │        └─ アセット内の kintone.events.on(...) はブリッジへ登録される
  │          │           change / submit など show 以外は、ここで exact type の native handler を遅延登録
  │          └─ ブリッジで現在の show をアセットへ直列配信し、最終の event を kintone へ返す
  └─ 2回目以降のshow(ページ送り、編集→詳細への戻り等)
        └─ ブリッジへ配信するだけ。購読者0件なら event を同期でそのまま返す
```

- **ゲートは画面種別ごと**に持つ。詳細画面と編集画面は同じページ内で行き来するため、
  「最初のshowで全アセットを評価」にすると、詳細画面から入ったときに編集画面向けアセットの評価時機を誤る。
  画面種別ごとに初回showで、その画面向けかつ未評価のアセットだけを評価する。1アセットは1ページで最大1回しか評価しない。
- アセットの評価はページ内で1回だけ(ADR-3は維持)。適用画面の判定は評価時と配信時の両方で行う。
  `screens: ['detail']` のアセットが `edit.show` を購読しても配信しない。
- CSSは画面遷移のたびに、適用画面に合わせて `<style>` の `disabled` を切り替える。ページ内遷移で詳細用CSSが編集画面に残らないようにする。
- 取得はページ読み込みにつき1回(`inflight` promiseを共有)。取得開始はdesktop.jsの評価直後で、
  kintone本体がフォームやレコードを読み込むのと並行に走る。**ゲートで待つのは `max(0, 取得完了 − show発火)` だけ**である。

### 2-4. 失敗時とタイムアウト

| 状況 | 挙動 |
| --- | --- |
| 取得がタイムアウト(`GATE_TIMEOUT_MS`、暫定3秒) | eventをそのまま返して画面を先へ進める。その後に取得できたら**CSSだけ**適用し、JSは評価しない。ランチャーに「カスタマイズの読み込みが間に合いませんでした。保存前チェックなどは動いていません」+ 再読み込みボタン |
| 取得失敗(ネットワーク / 403 / 404 / 上限超過) | JSもCSSも適用しない。ランチャーに原因別のエラーを表示する |
| アセット0件 | 取得完了でゲートを抜ける |
| セーフモード | ゲートを作らない。showハンドラは同期でeventを返す |
| JS評価中の例外 | そのアセットだけ失敗扱い(エラー隔離は旧設計のまま)。ゲートは必ずeventを返す |

タイムアウト後に遅れて届いたJSを評価しないのは、「一部のイベントだけ動く」中途半端な状態を作らないためである。
旧設計のリプレイは「showのDOM副作用は動くが返却eventは反映されない」という、説明しにくい意味論を持っていた。
ゲートにしたことで、アセットは**全部正しく動くか、動かないことが明示されるか**のどちらかになる。

タイムアウト時は、アセットが担っていた保存前チェックも動かない。これは可用性を優先した判断であり、
ランチャーの表示で必ず利用者に知らせる。保存前チェックが業務上必須なら、アセットではなく
kintone標準の入力制限・プロセス管理・通常のJSカスタマイズで担保すべきである(08 で導入判断者へ伝える)。

### 2-5. アセットへ渡す `kintone` をファサードにする

```ts
const factory = new Function('kintone', 'context', `"use strict";\n${asset.code}\n//# sourceURL=...`);
factory(createAssetKintone(asset, bridge, grants), context);
```

アセットのコード内の識別子 `kintone` は引数を参照する。ファサードは本物の `kintone` のプロパティを写した新しいオブジェクトとし、
次だけを差し替える。本物をプロトタイプに持たせると `Object.getPrototypeOf(kintone)` で素通りできるため、そうしない。
`Proxy` は、本物のプロパティが凍結されていると不変条件違反になるため使わない。

| メンバー | 差し替え後 |
| --- | --- |
| `kintone.events.on / off` | ブリッジへ登録・解除する。そのアセットのハンドラだけを扱う |
| `kintone.api`(`url` / `urlForGet` / `getConcurrencyLimit` を含む) | 権限を判定してから本物へ委譲する(3章) |
| `kintone.proxy` / `kintone.proxy.upload` | 外部通信の設定と通信先リストで、呼び出しごとにURLを判定する(3-3-2) |
| `kintone.plugin.app.proxy` / `proxy.upload` | 常に拒否する(本プラグインのAI用endpointを含む、他プラグインの認証済みproxyの流用を防ぐ) |
| `kintone.getRequestToken` | 書き込み系権限が1つも無いアセットには返さない(3-4) |
| それ以外 | 本物をそのまま返す |

これで得られるもの:

- **AIも人も、普通のkintoneカスタマイズの書き方(`kintone.events.on`)のままでよい。** 旧設計ではAIに `context.on` を
  使わせるためにシステムプロンプトで何度も念押しする必要があった。学習データにある大量のkintoneコードと同じ書き方で正しく動く。
- ハンドラの持ち主(どのアセットか)が登録時点で確定するので、エラー隔離・サーキットブレーカー・権限判定が同じ単位で扱える。
- `context` は現在の画面・アセット自身のメタ情報・ログ用だけに縮小する。

### 2-6. 消えるもの

| 旧設計の要素 | 扱い |
| --- | --- |
| `asset-cache.ts`(localStorage同期キャッシュ) | 削除 |
| 同期予算 256KiB / 30件(ADR-28) | 削除。評価時間の計測と警告だけ残す |
| localStorageのeviction・LRU・quota処理(ADR-29) | 削除。ミュートとセーフモードのキーは数十byteなので不要 |
| `cacheTtlMinutes` 設定と24時間hard expiry | 削除 |
| showリプレイ | 削除。非同期処理の後で登録されたshowハンドラは、次のshowから呼ばれる |
| `context.on` | 削除。`kintone.events.on` を使う |
| 脅威T7(共有PCの残留privateキャッシュ)・T12(失効したコードがキャッシュから動く) | コードを端末に保存しなくなったため構造的に解消 |
| 「JSの更新があります」通知(↻バッジ) | 読み込むたびに最新なので、読み込み時の差分検知は不要。自分で保存した直後の「再読み込みで反映」だけ残す |

### 2-7. コストとP-1で測ること

ゲートで待つ時間は `max(0, 取得完了 − show発火)` で、同一ドメインへの `getRecords` 1回ぶんが上限の目安である。
取得はdesktop.jsの評価直後に始まり、kintone本体の初期化と重なるので、多くの場合は0に近いと見込むが、**実測するまで断定しない**。

| 測定 | 合格の目安(暫定) |
| --- | --- |
| ゲート待ち時間 p50 / p95(一覧・詳細・追加・編集 × Chrome / Firefox / Safari × 低速回線) | p95 150ms以下 |
| ゲート保留中に、追加・編集画面で入力できてしまうか。できる場合、返却eventで入力が上書きされるか | 挙動を記録し、UI文言と06へ反映 |
| 他プラグインのshowハンドラが、本プラグインの保留を待つか | 挙動を記録 |
| 100件 / 2MiBのアセットの評価時間 | 警告閾値を決める |

p95が目安を超えた場合の退避策(**既定では実装しない**):

1. **空アプリのヒント**: 対象座標とユーザーごとに「前回アセット0件だった」という真偽値だけをlocalStorageへ置き、
   0件だったアプリではゲートで待たない。見つかった場合はCSSだけ適用し、JSは「再読み込みで有効」と表示する。
   コード本文は保存しないので、T7/T12は再発しない。
2. **CSSだけのキャッシュ**(案E): FOUCが実測で問題になった場合だけ。

## 3. カスタマイズ単位の権限

### 3-1. 目的と限界

アセットは利用者のセッションで動くので、何もしなければ**利用者ができることは全部できる**。
AIが意図しない一括更新・削除を書く、公開されたカスタマイズが知らないうちにレコードを書き換える、という不安に対して、
「このカスタマイズは何をしてよいか」をアセットごとに宣言し、宣言外の操作を実行時に止める。

ただし**これは安全装置であって、檻ではない**。アセットはkintoneのDOMへアクセスできるメインスレッドのコードであり、
`document.defaultView` や iframe、`window.kintone` を経由すれば、ファサードを通らずに本物のAPIへ到達できる(ADR-4)。
権限設定が止めるのは「宣言していない操作を、正規の書き方でうっかり行うこと」であり、悪意あるコードを止める境界は
引き続き**公開権限とアセット管理アプリのアクセス権**である(08)。UIとドキュメントでこの区別を曖昧にしない。

迂回できる書き方は静的に検出し、見つかったアセットは**「制限なし」を明示的に付与しない限り実行しない**(3-4)。
これにより「権限を付けたのに実は何でもできる」状態が、黙って存在することはなくなる。

### 3-2. 権限の種類

| 権限 | 既定 | 対象 |
| --- | --- | --- |
| 読み取り(GET) | **常に許可**(切り替え不可) | kintone REST APIのGET、および読み取りと同等の操作(3-3) |
| 追加(POST) | 禁止 | レコード追加、コメント投稿など |
| 更新(PUT) | 禁止 | レコード更新、ステータス変更、作業者変更など |
| 削除(DELETE) | 禁止 | レコード削除、コメント削除 |
| 外部通信(指定先のみ) | 禁止 | `kintone.proxy`、CSSの外部 `url()` / `@import` のうち、**通信先リストに一致するURLだけ**(3-3-2) |
| 外部通信(すべて) | 禁止 | 同上を送信先を問わず許可する |
| 制限なし | 禁止 | 3-4の迂回パターンを含むコードの実行。付与すると上記すべてを許可したのと同じ扱い |

**「外部通信」を読み取りと別に持つことが、GETを既定許可にできる理由である。**
GETで読めるのは利用者が元々見られるデータだけで、それ自体は新たな漏洩ではない。漏洩になるのは、それを外へ送るときである。
外部への出口を閉じておけば、GETを既定で開けても情報漏洩の経路は増えない。逆に、外部通信を権限に含めないと、
「GETだけ許可」のアセットが読んだデータを外へ送れてしまい、GETの既定許可が危険になる。

同じ理由で、外部通信は**送信先を指定して許可するのを基本**にする。「指定先のみ」なら、出口は利用者が信頼して列挙した送信先に限られる。
「すべて」は、読み取れる全データを任意の送信先へ送れる状態であり、UIで毎回そう明示する(3-6)。

アプリ設定・スペース・プラグイン・cybozu共通管理のAPIへの書き込みは、**権限の種類として用意しない**(「制限なし」以外では常に拒否)。
アセットが担うべき操作ではなく、アプリ管理権限を持つ利用者の画面で動いたときだけ成功する、という環境依存の動作を避ける。

### 3-3. kintone REST APIの分類

`classifyKintoneRequest(url, method, body)` は純粋関数とし、表駆動でテストする。
URLは `kintone.api.url()` の戻り値(絶対URL)と相対パスのどちらも受け、ゲストスペース形式 `/k/guest/{id}/v1/` は `/k/v1/` へ正規化する。

| リクエスト | 必要な権限 | 理由 |
| --- | --- | --- |
| `GET` すべて | 読み取り | |
| `POST /k/v1/records/cursor.json` | 読み取り | カーソル作成は大量取得の手段であり、データを変更しない |
| `DELETE /k/v1/records/cursor.json` | 読み取り | カーソルの後片付け。禁止すると取得処理が後始末できない |
| `POST /k/v1/record.json`, `records.json` | 追加 | |
| `POST /k/v1/record/comment.json` | 追加 | |
| `PUT /k/v1/record.json`, `records.json` | 更新 | |
| `PUT /k/v1/record/status.json`, `records/status.json`, `record/assignees.json` | 更新 | プロセス管理の操作もレコードの変更である |
| `DELETE /k/v1/records.json`, `record/comment.json` | 削除 | |
| `POST /k/v1/file.json` | 追加 **または** 更新 | ファイルのアップロード単体ではレコードは変わらず、添付に使うにはレコードの追加か更新が要る |
| `POST /k/v1/bulkRequest.json` | 中の各リクエストを同じ規則で分類した**和集合** | bulkRequestはPOSTだが中身は任意のメソッド。外側のメソッドだけで判定すると削除を通してしまう |
| `/k/v1/preview/**`, `/k/v1/app/**`, `/k/v1/app.json`, `/k/v1/apps.json`, `/k/v1/space/**` などへのGET以外 | 制限なしのみ | アプリ・スペース設定の変更 |
| 上記以外のパス(非公開APIを含む)へのGET以外 | 制限なしのみ | 未知の操作は拒否側へ倒す |
| URLを解釈できない | 制限なしのみ | 同上 |

書き込み先のアプリは問わない(v1)。「対象アプリ以外への書き込みを別権限にする」はv1.1候補(3-8)。

### 3-3-2. 外部通信の範囲(通信先の指定)

外部通信は3段階で設定する。

| 設定 | 「権限」フィールドの値 | 挙動 |
| --- | --- | --- |
| 禁止(既定) | どちらも未選択 | 外部通信はすべて拒否 |
| 指定先のみ | `外部通信(指定先のみ)` | 「通信先」フィールドのパターンに一致するURLだけ許可 |
| すべて | `外部通信(すべて)` | 送信先を問わず許可 |

両方が選択されているレコード(管理アプリを直接編集した場合に起こりうる)は、**狭いほうの「指定先のみ」として扱い**、一覧に設定不備を出す。
「制限なし」は「すべて」を含む。

**通信先の書き方**(アセット管理アプリの文字列(複数行)フィールド「通信先」。1行に1パターン):

```text
# 郵便番号検索API
https://zipcloud.ibsnet.co.jp/api/
# Google Fonts(CSS)
https://fonts.googleapis.com
https://fonts.gstatic.com
```

| 書き方 | 一致する範囲 |
| --- | --- |
| `https://api.example.com` | そのオリジン(スキーム・ホスト・ポートが完全一致)の全パス |
| `https://api.example.com/v1/` / `https://api.example.com/v1` | そのオリジンで、パスが `/v1` と一致するか `/v1/` から始まるもの。**パスセグメント境界で判定**し、`/v10` や `/v1evil` には一致しない |

- 空行と `#` で始まる行は無視する。上限は50行、1行2KiB。
- パターンは保存時・読み込み時に `new URL()` で正規化する(ホストの小文字化、国際化ドメインのpunycode化、既定ポートの除去、パスの `..` 解決)。
- 次のパターンは**無効**として扱い、一致判定に使わない。UIでは赤字で理由を出す。
  - `http:` / `https:` 以外のスキーム、ホストなし、ユーザー情報(`user:pass@`)、クエリ(`?`)、フラグメント(`#`)を含むもの
  - ワイルドカード(`*`)を含むもの(v1ではサブドメインのワイルドカードを提供しない。3-8)
- `http:` のパターンは有効だが、「暗号化されない通信です」と警告する。

**一致判定**(`matchExternalTarget(url, patterns)`、純粋関数):

1. 要求URLを `new URL(url)` で解析する。**絶対URLでなければ拒否**(相対URLをkintoneのオリジン基準で解決しない)。
2. ユーザー情報を含むURLは拒否する(`https://api.example.com@evil.example/` のような見た目の偽装を防ぐ)。
3. オリジンが完全一致するパターンを探す。文字列の前方一致は使わない(`https://api.example.com.evil.example` を通さないため)。
4. パスは正規化後に、セグメント境界での前方一致で判定する。`/v1/../admin` は `/admin` として判定される。
5. クエリとフラグメントは判定に使わない。送信先を信頼して許可する設計なので、何を送るかはコードのレビューで確認する。

対象ごとの強制:

| 対象 | 強制方法 |
| --- | --- |
| `kintone.proxy(url, ...)` / `kintone.proxy.upload(url, ...)` | ファサードで呼び出しごとに判定。URLが実行時に組み立てられても正しく判定できる |
| CSSの `url(...)` / `@import` / `image-set(...)` / `@font-face` の `src` | 静的に全URLを抜き出して判定する。1つでも一致しなければ、そのCSSアセットは適用しない。相対URL・`data:`・kintoneと同一オリジンは外部通信に数えない |
| JSのコード中にある外部URLの文字列リテラル | **判定に使わない(情報表示のみ)**。`<a href>` のリンクなど正当な用途があるため。詳細画面に「コード内の外部URL」として一覧し、通信先リストとの一致を表示してレビューを助ける |

`kintone.proxy` がリダイレクト(3xx)をサーバー側で追従するかは公式に記載が無い。追従する場合、通信先リストが制御するのは**最初の送信先だけ**になる。
P-1で確認し、追従するなら詳細画面の説明に「許可した送信先がリダイレクトした先へは制御が及ばない」と明記する。

拒否の記録と診断表示には、要求URLのオリジンとパスだけを出し、クエリは出さない(クエリに業務データが載りうるため)。

### 3-4. 強制の仕組み

**① ファサードでの実行時判定**(2-5)。`kintone.api` の呼び出しごとに分類し、付与されていなければ本物を呼ばずに拒否する。

- Promise形式の呼び出しには `Promise.reject(error)`(ネイティブのPromise)を返す。`kintone.Promise` は古い仕様のため使わない。コールバック形式なら失敗コールバックを非同期で呼ぶ。
- エラーは `{ code: 'AI_CUSTOMIZE_PERMISSION_DENIED', message, required, method, path }`。アセット側の `catch` で扱える形にする。
- submitハンドラ内で拒否された場合、それはハンドラの例外になり、保存を止める(ADR-23のfail closedと同じ扱い)。
- 権限は呼び出しのたびに現在値を参照する。パネルで権限を外すと、そのタブでも**次の呼び出しから**止まる。

**② CSRFトークンという関所**。セッション認証で `fetch` / `XMLHttpRequest` からPOST・PUT・DELETEを送るには、
CSRFトークンの付与が必須である([認証](https://cybozu.dev/ja/kintone/docs/rest-api/overview/authentication/))。
ファサードの `kintone.getRequestToken()` を書き込み権限の無いアセットへ返さないことで、「`fetch` で直接書き込む」
という正規ではないが素朴な書き方も、kintoneのサーバー側で失敗させられる。GETはトークン不要なので影響しない。

**③ 迂回パターンの静的検出**。`detectCapabilityUsage(code)` が次を返す。承認時と実行時で同じ関数を使う。

```ts
type CapabilityUsage = {
  /** kintone.api の第2引数がリテラルのとき、そのメソッドと行番号 */
  apiCalls: { method: 'GET' | 'POST' | 'PUT' | 'DELETE' | 'unknown'; path: string | null; line: number }[];
  /** kintone.proxy。target はリテラルのときだけURL、組み立てられたURLは null(実行時にファサードが判定) */
  external: { line: number; target: string | null }[];
  /**
   * kintone.proxy を通らない外部リソースの読み込み(img.src = 'https://…'、setAttribute('src', …)、
   * HTML文字列の <img src> / <form action> / <link href>、文字列中の url(…))。
   * CSSの外部url()と同じ基準で、実行前に外部通信の設定と照合する。組み立てられたURLは null
   */
  resources: { line: number; target: string | null }[];
  /** JS内の外部URLの文字列リテラル(情報表示のみ) */
  urlLiterals: { line: number; url: string }[];
  /** ファサードを通らずに本物へ到達しうる書き方 */
  bypass: { pattern: string; line: number }[];
};
```

迂回パターン(文字列・コメントを除いたトークン列で判定する。正規表現を生のコードへ当てない):

| 分類 | パターン |
| --- | --- |
| 本物の `kintone` への到達 | `window.kintone`、`globalThis`、`document.defaultView`、`contentWindow`、`window[...]`(計算プロパティ)、`window` と別名(`self`、`top`、`parent`、`frames`、`opener`)を値として持ち出す書き方(`const g = self` や `self[...]`。別名は、その位置から見えるスコープで同名の変数・引数が宣言されていれば、その変数とみなす) |
| ネットワークの直接利用 | `fetch`、`XMLHttpRequest`、`navigator.sendBeacon`、`WebSocket`、`EventSource` |
| 実行時のコード生成・読み込み | `eval`、`Function`、`.constructor`、`import(`、文字列を渡す `setTimeout` / `setInterval`、`createElement('script')` / `('iframe')`、`Worker`、`document.write` / `writeln`、文字列中の `<script` / `<iframe` / HTMLのインラインイベント属性(`<img onerror=…>`) / コードを実行する `javascript:` URL(`javascript:void(0)` などの何もしない形は除く) |
| 非公開のkintone内部 | `cybozu` グローバル |

実行時の規則:

- `bypass` が1件でもあり、「制限なし」が付与されていないJSアセットは**実行しない**。一覧に理由と行番号を出す。
- CSSアセットは、外部 `url()` / `@import` の全URLが外部通信の設定(3-3-2)で許可されていなければ適用しない(CSSは実行時に迂回できないので静的判定で足りる)。
- JSアセットの `resources`(`kintone.proxy` を通らない外部リソースの読み込み)も、CSSと同じ基準で実行前に照合し、
  1つでも許可されていなければ実行しない。組み立てられた送信先(`null`)は「すべて」でだけ許可する。
  kintoneと同一オリジン・相対URLは外部通信に数えない。
- 検出しないもの: 変数だけで渡された送信先(`img.src = url`)と、画面遷移(`location` への代入、`open()`、`<a href>`)。
  画面遷移は利用者に見える操作で、別レコードへの移動など正規の用途が多いため、静的検出の対象にしない(3-1の限界)。
- AIの `write_asset` は、`bypass` を含むコードの保存を拒否してAIに書き直させる(正規の書き方が必ず存在するため)。
  「制限なし」と「外部通信(すべて)」はAIから要求できず、人が詳細画面で付与する。AIが要求できるのは通信先を列挙した「指定先のみ」だけである。

静的検出の目的は、**迂回の余地があるコードを黙って「権限つき」として扱わないこと**である。検出をすり抜ける書き方は作れるが、
それは実行許可を与える人(公開権限者)のレビューで止めるべき悪意であり、3-1の限界として明記する。

### 3-5. 保存場所とkintone側のアクセス権

アセット管理アプリに**チェックボックス「権限」**(`permissionsFieldCode`、必須)を追加する。選択肢は
`追加(POST)` / `更新(PUT)` / `削除(DELETE)` / `外部通信(指定先のみ)` / `外部通信(すべて)` / `制限なし` で、値はプラグイン設定で対応付ける(03)。
**既定は全て未選択**(= 読み取りのみ)。未知の値は無視する(安全側)。

通信先は**文字列(複数行)「通信先」**(`externalUrlsFieldCode`、任意)に保存する。対応付けていない環境では「指定先のみ」を選んでも
通信先が空として扱われ、外部通信は全て拒否される。設定画面でその旨を警告する。「通信先」も「権限」と同じくレコードアクセス権で守る。

誰が変えられるかは、既存のレコードアクセス権の設計(08 2-1)にそのまま乗る。

| アセット | 権限を変更できる人 | 根拠 |
| --- | --- | --- |
| private | 作成者本人 | privateは作成者の画面でしか動かず、作成者自身の権限を超えない。権限は「AIの書いたコードからの自己防衛」として働く |
| public | publicレコードを編集できる人(= カスタマイズ管理者) | 一般ユーザーはpublicレコードを編集できないレコードアクセス権にしてある |

kintoneのフィールドアクセス権はレコードの値で条件を変えられないため、「権限」フィールドへ個別のフィールドアクセス権は設定しない。
publicレコードの保護はレコードアクセス権で行う。private→public化は `scope` フィールドのアクセス権で公開権限者に限定済みなので、
**公開する人が権限の内容も承認する**ことになる。公開の承認カードでは、権限と、その権限を使うコード行を並べて表示する。

### 3-6. UI

- 一覧の行: 付与済みの書き込み系権限をチップで出す(`更新` `削除` `外部: 2件` `外部: すべて`。読み取りは出さない)。「外部: すべて」と「制限なし」は警告色。
- 詳細画面: 権限ごとのスイッチ。各スイッチの横に、`detectCapabilityUsage` が見つけた**その権限を使う行**を表示する。
  付与するときは「このコードは○行目でレコードを更新します」を確認させる。使っていない権限の付与には「このコードは使っていません」と表示する。
  スイッチの活性は `record.editable` かつ `fields[permissionsFieldCode].editable`(06の表と同じ規則)。
- 拒否の記録: ファサードが止めた操作を、アセットごとに「○○が レコード更新(PUT /k/v1/record.json)を試みましたが、許可されていないため止めました」
  として一覧の ⚠ に出す。権限を変更できる人には「許可する」ボタンを添え、押すと詳細画面の該当スイッチへ移動する(その場で付与はしない)。
- 外部通信: 「禁止 / 指定先のみ / すべて」の切り替えと、通信先の一覧編集。コードが使っているのにリストに無い送信先には「追加」ボタンを出す(押すと確認のうえ追加)。
  「すべて」を選ぶときは「このカスタマイズは、あなたが読めるデータを任意の送信先へ送れるようになります」と確認する。
- AI: `write_asset` の承認カードに、要求された権限・通信先と検出結果を並べる(07)。

### 3-7. 変更の反映

旧設計(同期キャッシュ)では、権限を外してもキャッシュのTTLからhard expiryまで古い状態で動きうる。
起動ゲートでは毎回最新のレコードから権限を読むため、**権限の変更は他の利用者にも次の画面読み込みで必ず反映される**。
権限を変更したタブでは、**狭める変更(取り消し・無効化・削除・コードの書き換え)だけ**を即時に反映する。
ファサードは現在値を参照するので次の呼び出しから止まり、まだ評価していないJS(後の画面遷移で評価するもの)は
パネルで外したものを評価せず、狭めた権限で迂回パターン・外部リソースを判定する。
広げる変更(付与・通信先の追加・有効化)は、評価済みのコードが保存前の版かもしれないため、再読み込みしてから効かせる。
パネルの一覧が取得時点より古くても、実行中の権限が広がることはない(`narrowGrants`)。
起動方式の見直しと権限モデルは独立した改善ではなく、前者が後者の実効性を支えている。

### 3-8. v1では入れないもの(v1.1候補)

| 候補 | 内容 | 入れない理由 |
| --- | --- | --- |
| 通信先のワイルドカード | `https://*.example.com` のようなサブドメインの一括指定 | 公開サフィックス(`*.co.jp` など)を安全に弾くには Public Suffix List が要る。実例を見てから入れる |
| 書き込み先の限定 | 書き込み系権限を「対象アプリのみ / 指定アプリ」に絞る | bodyの `app` を解釈すれば実装できるが、ルックアップ・関連レコードの更新など実例を集めてから粒度を決めたい |
| ローカル制限 | 権限を変更できない利用者が、publicアセットの書き込みを自分のブラウザでだけ止める | ローカル無効化(05 8章)で当面代替できる。「部分的に動くpublicアセット」の問い合わせ対応が増える |
| 迂回パターンの実行時追跡 | `fetch` / XHR をパッチし、スタックの `sourceURL` から呼び出し元アセットを特定して止める | ページ全体とkintone本体の通信へ割り込むため影響が大きい。静的検出 + 「制限なし」で方針を明示するほうが予測可能 |
